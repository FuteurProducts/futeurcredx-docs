# AI Operator Rules for LumiqAI

This document defines the mandatory constraints, behaviors, and operational rules for any AI agent (Claude, Claude Code, Lovable AI, n8n AI nodes, LangGraph agents, or future AI tools) operating within the LumiqAI platform.

---

## Document Authority

**Classification**: MANDATORY CONSTRAINTS  
**Enforcement**: All AI agents MUST comply  
**Violations**: Must be flagged and escalated to humans  
**Updates**: Append-only; deprecation requires human approval

---

## Core Principles

### Principle 1: Humans Approve All Changes

AI agents propose; humans decide. No AI agent may:
- Merge pull requests
- Deploy to production
- Delete production data
- Revoke security credentials
- Modify RLS policies without human review

### Principle 2: Read Before Write

Before modifying any artifact (code, documentation, configuration), AI agents MUST:
1. Read the existing content in full
2. Understand the current state
3. Check for conflicts with existing decisions
4. Only then propose changes

### Principle 3: Explicit Scope Always

Every operation must have explicit scope:
- `tenant_id` for tenant-specific operations
- `portfolio_id` for portfolio-specific operations
- File paths for code changes
- Decision IDs when referencing constraints

### Principle 4: Audit Everything

Every action taken by an AI agent must be logged to the `agent_actions` table with:
- `action_type`: What was attempted
- `payload`: Input parameters
- `result`: Outcome or error
- `timestamp`: When it occurred

## Mandatory Pre-Checks

Before proposing any change, AI agents MUST consult these documents in order:

### Check 1: System Decisions

**File**: `docs/LUMIQAI_SYSTEM_DECISIONS.md`

- Identify any Active decisions that relate to the proposed change
- If a conflict exists, STOP and ask for human clarification
- Never override an Active decision without explicit human instruction

### Check 2: Architecture Documentation

**Files**:
- `docs/README.md` (architecture overview)
- `docs/LUMIQAI_SYSTEM_OPERATOR_HANDBOOK.md` (operational rules)
- `docs/LUMIQAI_FRONTEND_IMPLIED_BACKEND_CONTRACT.md` (API contracts)

### Check 3: Existing Code Patterns

Before writing new code:
- Search for similar existing patterns in the codebase
- Follow established conventions
- Do not introduce new patterns without justification

## Prohibited Actions

AI agents are EXPLICITLY FORBIDDEN from:

### Code Prohibitions

| Action | Reason |
|--------|--------|
| Editing `src/integrations/supabase/client.ts` | Auto-generated by Supabase |
| Editing `src/integrations/supabase/types.ts` | Auto-generated by Supabase |
| Editing `supabase/config.toml` | Managed by Lovable Cloud |
| Editing `.env` | Managed by Lovable Cloud |
| Editing `package.json` directly | Use `lov-add-dependency` / `lov-remove-dependency` |
| Editing `supabase/migrations/` | Read-only migration history |
| Writing direct database queries in frontend | Must use BFF layer |
| Hardcoding API keys or secrets | Use secrets management |
| Using arbitrary color values | Must use design tokens |

### Architectural Prohibitions

| Action | Reason |
|--------|--------|
| Bypassing BFF for data access | Violates SD-001 (BFF architecture) |
| Removing `portfolioId` requirements | Violates SD-002 (tenant isolation) |
| Disabling audit logging | Violates SD-003 (auditability) |
| Direct database access from automation | Violates SD-007 (automation constraints) |
| Auto-merging PRs | Violates SD-006 (human approval) |

### Data Prohibitions

| Action | Reason |
|--------|--------|
| Deleting production data | Requires human approval |
| Modifying RLS policies without review | Security-critical |
| Accessing cross-tenant data | Violates isolation |
| Storing PII in logs | Compliance violation |

## Required Behaviors

### When Modifying Code

1. **Check file contents first**: Never edit a file without viewing its current contents
2. **Prefer search-replace**: Use `lov-line-replace` over full file rewrites
3. **Parallel operations**: Make independent changes simultaneously
4. **Maintain patterns**: Follow existing code style and conventions
5. **Update documentation**: If code changes affect documented behavior

### When Modifying Database

1. **Use migration tool**: All schema changes via `supabase--migration`
2. **Include RLS policies**: Every new table needs RLS
3. **Never use CHECK constraints with time functions**: Use validation triggers instead
4. **Never modify reserved schemas**: `auth`, `storage`, `realtime`, `supabase_functions`, `vault`

### When Modifying Edge Functions

1. **Use shared utilities**: Import from `_shared/` directory
2. **Authenticate requests**: Call `authenticateRequest()` from `_shared/auth.ts`
3. **Log audit events**: Call `writeAuditEvent()` for sensitive operations
4. **Return standardized responses**: Use `successResponse()` / `errorResponse()`
5. **Require portfolioId**: For any data-fetching endpoint

### When Creating New Features

1. **Check decision ledger**: Ensure no conflicts with existing decisions
2. **Follow BFF pattern**: Frontend → BFF Edge Function → Database
3. **Add audit hooks**: Client-side via `useAuditEmit`, server-side via `writeAuditEvent`
4. **Use design tokens**: No arbitrary colors; use semantic tokens
5. **Handle errors**: Use `BffErrorBoundary` pattern

## Decision Conflict Resolution

When a proposed change conflicts with an existing decision:

### Step 1: Identify the Conflict

```
CONFLICT DETECTED:
- Proposed Action: [describe what is being proposed]
- Conflicting Decision: SD-XXX
- Conflict Type: [direct violation | partial conflict | unclear boundary]
```

### Step 2: Do Not Proceed

AI agents MUST NOT attempt workarounds or interpretations. Stop and escalate.

### Step 3: Request Human Clarification

```
CLARIFICATION NEEDED:
- The proposed change conflicts with SD-XXX.
- Please advise:
  1. Proceed with the change (will note as decision override)
  2. Modify the approach to comply with SD-XXX
  3. Deprecate SD-XXX and create a new decision
```

### Step 4: Document Resolution

If humans approve an override:
- Add a new entry to the decision ledger
- Reference the superseded decision
- Document the rationale for the change

## Error Handling Rules

### When BFF Calls Fail

| Error Code | AI Agent Behavior |
|------------|-------------------|
| 401 | Session expired; do not retry; inform user |
| 403 | Access denied; do not attempt bypass; inform user |
| 422 | Missing required parameter; check `portfolioId`; inform user |
| 500 | Server error; may retry once; log and report |
| Network error | May retry with exponential backoff; max 3 attempts |

### When Code Changes Fail

| Failure Type | AI Agent Behavior |
|--------------|-------------------|
| Syntax error | Fix immediately; do not leave broken code |
| Type error | Analyze types; fix or ask for clarification |
| Runtime error | Check console logs; attempt fix; report if unclear |
| Test failure | Do not ignore; fix or document why fix is deferred |

### When Uncertain

If an AI agent is uncertain about:
- Whether a change violates a decision → Ask human
- Whether a pattern is correct → Search for existing examples first
- Whether scope is appropriate → Ask human
- Whether action is safe → Ask human

**Default behavior when uncertain: STOP and ASK.**

## Communication Rules

### With Humans

1. **Be concise**: Brief responses unless detail is requested
2. **Be explicit**: State what was done, not what might happen
3. **Cite sources**: Reference decision IDs, file paths, line numbers
4. **Admit uncertainty**: If unsure, say so
5. **Suggest options**: When multiple valid approaches exist

### With Other AI Agents

1. **Use structured data**: JSON for inter-agent communication
2. **Include context**: Reference relevant decisions and files
3. **Log interactions**: All agent-to-agent communication in `agent_actions`

### When Reporting Actions

```
ACTION COMPLETED:
- Type: [code change | database migration | documentation update]
- Files Modified: [list paths]
- Lines Changed: [summary]
- Decisions Referenced: [SD-XXX if applicable]
- Tests Affected: [if any]
```

## Specific Agent Rules

### Claude Code (via GitHub)

- ONLY creates pull requests; never commits directly
- MUST follow issue template format for instructions
- MUST reference the triggering issue in PR description
- Expected response time: 5-30 minutes
- If no PR after 60 minutes: alert operators

### Lovable AI (Interactive)

- MUST check file contents before editing
- MUST use `lov-line-replace` for most edits
- MUST run parallel operations when possible
- MUST verify changes via console logs or browser tools
- MUST NOT exceed 2 sentences for simple confirmations

### n8n Workflows (Automation)

- MUST NOT write application code
- MUST NOT access database directly
- MUST use BFF endpoints for all data operations
- MUST use n8n credential store for secrets
- MUST log all actions to `agent_actions` table

### Future LangGraph Agents

- MUST operate within defined action boundaries
- MUST NOT make autonomous decisions on sensitive operations
- MUST log all reasoning steps
- MUST request human approval for irreversible actions

## Memory and Context Rules

### What AI Agents Should Remember

- Active system decisions (SD-XXX entries)
- Current architecture patterns
- File modification history within session
- Unresolved conflicts or questions

### What AI Agents Should NOT Assume

- User intent beyond explicit statements
- Approval for undiscussed changes
- That previous sessions' context persists
- That documentation is outdated (it's maintained)

### Context Refresh Triggers

AI agents should re-read documentation when:
- Starting a new session
- User mentions system architecture
- Proposed change touches core infrastructure
- Error suggests architectural confusion

## Compliance Verification

### Self-Check Before Action

AI agents should verify:

```
PRE-ACTION CHECKLIST:
[ ] Read current file contents
[ ] Checked decision ledger for conflicts
[ ] Verified scope (tenant/portfolio/user)
[ ] Identified affected audit events
[ ] Confirmed no prohibited actions
[ ] Prepared rollback approach if needed
```

### Post-Action Verification

After completing an action:

```
POST-ACTION CHECKLIST:
[ ] Change compiles/builds successfully
[ ] No console errors introduced
[ ] Tests pass (if applicable)
[ ] Documentation updated (if needed)
[ ] Audit event logged (if sensitive)
```

## Escalation Procedures

### When to Escalate to Humans

| Situation | Escalation Action |
|-----------|-------------------|
| Decision conflict | Stop; present conflict; wait for resolution |
| Security concern | Stop; flag concern; do not proceed |
| Irreversible action | Request explicit approval before proceeding |
| Unclear requirements | Ask clarifying questions |
| Multiple valid approaches | Present options; let human choose |
| Error loop (3+ failures) | Stop; summarize attempts; ask for help |

### How to Escalate

```
ESCALATION:
- Issue: [brief description]
- Context: [relevant decisions, files, prior attempts]
- Options: [list possible resolutions]
- Recommendation: [if any, with rationale]
- Awaiting: [human decision before proceeding]
```
