## 1. Executive Summary

The LUMIQ AI Control Tower is a B2B SaaS dashboard that enables banks to manage SMB credit scoring, pre-qualification, underwriting, and portfolio risk monitoring. It is powered by the LUMIQ AI scoring engine and designed to be white-labeled for partner bank deployments.

**Phase 1** transformed the dashboard from a prototype-quality scaffold (rated 5.4/10 by a bank executive audit) into a production-grade fintech interface (audited at 9.5/10) modeled after Stripe, Mercury, and Plaid design patterns. This was achieved through:

- A complete design token system (CSS custom properties + Tailwind)
- Migration of 100+ files from hardcoded colors to semantic tokens
- Full dark mode support with a three-way toggle (light/dark/system)
- Interactive workflows: approve/decline, sort, filter, search, export
- Skeleton loading states, empty states, micro-interactions
- Live activity simulation for demo credibility
- Accessibility improvements (skip-to-content, ARIA labels, keyboard nav)
- Environment-aware sandbox/production indicator system

**Zero new runtime dependencies were added** — the entire overhaul uses Tailwind CSS configuration, CSS custom properties, and existing libraries (Framer Motion, Recharts, Radix UI).

## 2. What Existed Before Phase 1

### Initial State
The codebase arrived as a functional but visually inconsistent prototype:

| Area | Before State |
|---|---|
| **Colors** | ~239 files with hardcoded Tailwind colors (`bg-emerald-100`, `text-red-600`, `bg-slate-50`, `bg-white`) — no design tokens |
| **Dark Mode** | Not supported. `darkMode: ["class"]` was in Tailwind config but no toggle, no dark token values, hardcoded `bg-white` everywhere |
| **Typography** | Inconsistent — mix of `text-2xl font-semibold`, `text-lg font-bold`, raw sizes. No scale |
| **Elevation** | No shadow system. Cards had no depth hierarchy |
| **Tables** | Static display only — no sorting, filtering, search, or pagination |
| **Empty States** | None — tables showed nothing when empty |
| **Loading States** | None — instant render of hardcoded data with no loading indication |
| **Buttons** | Approve/Decline/Review buttons in underwriting were non-functional |
| **Environment Toggle** | Settings page used local `useState` disconnected from global context |
| **Export** | No CSV or PDF export capability |
| **Accessibility** | No skip-to-content, no ARIA labels on icon-only buttons |
| **Micro-Interactions** | No feedback animations, no number animations, no transitions |

### What Worked
- Component structure was well-organized (enterprise/, dashboard/, widgets/, etc.)
- Supabase schema and BFF service layer were architecturally sound
- shadcn/ui primitive components were properly installed
- Route structure and context providers were in place
- Demo data existed but was scattered across individual component files

## 6. Design Token System

### Philosophy
Every color in the UI maps to a **semantic purpose**, not a visual value. This enables:
- Dark mode via a single CSS class toggle
- White-labeling by changing 10-15 CSS variable values
- Consistent status indicators across all 266 components

### CSS Custom Properties (`src/index.css`)

#### Core Palette
| Token | Light | Dark | Usage |
|---|---|---|---|
| `--background` | `0 0% 100%` (white) | `222.2 84% 4.9%` (near-black) | Page background |
| `--foreground` | `222.2 84% 4.9%` | `210 40% 98%` | Primary text |
| `--card` | `0 0% 100%` | `222.2 84% 4.9%` | Card backgrounds |
| `--primary` | `221.2 83.2% 53.3%` | `217.2 91.2% 59.8%` | CTA buttons, links |
| `--muted` | `210 40% 96.1%` | `217.2 32.6% 17.5%` | Subtle backgrounds |
| `--muted-foreground` | `215.4 16.3% 46.9%` | `215 20.2% 65.1%` | Secondary text |
| `--border` | `214.3 31.8% 91.4%` | `217.2 32.6% 17.5%` | All borders |
| `--destructive` | `0 84.2% 60.2%` | `0 62.8% 30.6%` | Errors, declines |

#### Status Colors (Added in Phase 1)
| Token | Light | Dark | Usage |
|---|---|---|---|
| `--success` | `160 84% 39%` | `160 84% 45%` | Approvals, healthy, operational |
| `--warning` | `38 92% 50%` | `38 92% 55%` | Caution, pending review |
| `--info` | `217 91% 60%` | `217 91% 65%` | Informational, bureau status |

#### Surface & Elevation
| Token | Light | Dark | Usage |
|---|---|---|---|
| `--surface` | `210 40% 98%` | `224 71% 8%` | Page canvas (slightly off-white) |
| `--surface-raised` | `0 0% 100%` | `222 84% 7%` | Cards on surface |
| `--shadow-xs` | `0 1px 2px 0 rgb(0 0 0 / 0.03)` | `... / 0.1)` | Default card shadow |
| `--shadow-sm` | `0 1px 3px ...` | `... / 0.15)` | Card hover shadow |
| `--shadow-md` | `0 4px 6px ...` | `... / 0.2)` | Dropdowns, popovers |
| `--shadow-lg` | `0 10px 15px ...` | `... / 0.2)` | Modals, overlays |

### Tailwind Registration (`tailwind.config.ts`)

All tokens are registered in `theme.extend.colors` using the `hsl(var(--token))` pattern, making them available as standard Tailwind classes:

```tsx
// Usage examples
<div className="bg-surface" />           // Page background
<div className="bg-card" />              // Card background
<div className="text-foreground" />       // Primary text
<div className="text-muted-foreground" /> // Secondary text
<div className="text-success" />          // Green status text
<div className="bg-success/10" />         // Green tinted background
<div className="border-border" />         // Standard border
<div className="shadow-xs" />             // Resting elevation
<div className="hover:shadow-sm" />       // Hover elevation
```

### Typography Scale

| Class | Size | Weight | Line Height | Usage |
|---|---|---|---|---|
| `text-display` | 2.25rem (36px) | 700 | 2.5rem | Page titles |
| `text-headline` | 1.5rem (24px) | 600 | 2rem | Section headers |
| `text-title` | 1.125rem (18px) | 600 | 1.75rem | Card titles |
| `text-body` | 0.875rem (14px) | 400 | 1.25rem | Body text |
| `text-caption` | 0.75rem (12px) | 500 | 1rem | Labels, metadata |
| `text-overline` | 0.6875rem (11px) | 600 | 1rem | Overlines (0.05em tracking) |

### Color Migration Map
This is the mapping used when migrating hardcoded colors to tokens:

```
bg-emerald-100, bg-emerald-500/10, bg-green-100  →  bg-success/10
text-emerald-600, text-green-600                   →  text-success
bg-emerald-500, bg-green-500                       →  bg-success

bg-amber-100, bg-amber-500/10, bg-yellow-100      →  bg-warning/10
text-amber-600, text-yellow-600                     →  text-warning

bg-red-100, bg-red-500/10                          →  bg-destructive/10
text-red-600                                        →  text-destructive

bg-blue-100, bg-blue-500/10                        →  bg-info/10
text-blue-600                                       →  text-info

bg-slate-50                                         →  bg-surface
bg-white                                            →  bg-card
text-slate-900, text-gray-900                       →  text-foreground
text-slate-600, text-gray-600                       →  text-muted-foreground
bg-slate-100, bg-gray-100                           →  bg-muted
border-slate-200, border-gray-200                   →  border-border
```

**Exception:** Decorative/brand accent colors (violet, purple, pink, orange-500 for specific icons) remain hardcoded as they are intentional brand accents, not semantic status indicators.

## 9. State Management — React Contexts

### ThemeContext (`src/contexts/ThemeContext.tsx`)
Manages light/dark/system theme mode.

| Property | Type | Description |
|---|---|---|
| `theme` | `'light' \| 'dark' \| 'system'` | User-selected mode |
| `resolvedTheme` | `'light' \| 'dark'` | Actual applied mode |
| `setTheme` | `(t: Theme) => void` | Switch mode |

**Storage:** `localStorage` key `lumiq-theme`, defaults to `'light'`.

**Mechanism:** Adds/removes `.dark` class on `<html>` element. When `system` is selected, listens to `prefers-color-scheme` media query.

### EnvironmentContext (`src/contexts/EnvironmentContext.tsx`)
Manages sandbox/production environment switching.

| Property | Type | Description |
|---|---|---|
| `currentEnvironment` | `'sandbox' \| 'production'` | Active environment |
| `sandboxConfig` | `EnvironmentConfig` | Sandbox API URL, status |
| `productionConfig` | `EnvironmentConfig` | Production API URL, status |
| `switchEnvironment` | `(env) => Promise<void>` | Switch with 800ms simulated sync |
| `isSwitching` | `boolean` | Loading state during switch |
| `getApiBaseUrl` | `() => string` | Returns active API URL |

**Storage:** `localStorage` key `lumiq-environment`.

**API URLs:**
- Sandbox: `https://sandbox.lumiqai.com/v1`
- Production: `https://api.lumiqai.com/v1`

### PortfolioContext (`src/contexts/PortfolioContext.tsx`)
Manages active portfolio selection. All BFF API calls require a `portfolioId`.

| Property | Type | Description |
|---|---|---|
| `portfolioId` | `string \| null` | Active portfolio ID |
| `portfolio` | `Portfolio \| null` | Active portfolio object |

## 11. BFF (Backend-for-Frontend) Service Layer

### Architecture

```
Browser → BFF Client → Supabase Edge Functions → Supabase DB
           (client.ts)    (serverless)           (PostgreSQL)
```

The BFF layer is fully implemented and ready for live data. It currently isn't used because `DEV_BYPASS_AUTH = true` and pages render demo data directly. When auth is enabled and Supabase Edge Functions are deployed, the same components can consume live data.

### BFF Client (`src/services/bff/client.ts`)

- **Base URL:** `${VITE_SUPABASE_URL}/functions/v1`
- **Auth:** Bearer token from `supabase.auth.getSession()`
- **Tenant Isolation:** Every request includes `portfolioId` as query parameter
- **Response Envelope:** `BffResponse<T>` (single item) or `BffListResponse<T>` (list with pagination)
- **Error Handling:** Typed `BffError` with `code`, `message`, `details`, `requestId`

### Domain Services

| Service | File | Key Endpoints |
|---|---|---|
| **Customers** | `bff/customers.ts` | `GET /customers` (list), `GET /customers/:id` (dossier), `GET /customers/lifecycle`, `GET /customers/health` |
| **Scores** | `bff/scores.ts` | `GET /scores`, `POST /scores/pull`, `GET /scores/distribution`, `GET /scores/bureau-status/:id` |
| **Offers** | `bff/offers.ts` | `GET /offers`, `POST /offers/:id/accept`, `POST /offers/:id/decline` |
| **Applications** | `bff/applications.ts` | `GET /applications`, `POST /applications`, `PATCH /applications/:id`, `GET /applications/pipeline` |
| **Reports** | `bff/reports.ts` | `POST /reports` (async create), `GET /reports/:id` (poll), `GET /reports/:id/download` |
| **Risk** | `bff/risk.ts` | `GET /risk/summary`, `GET /risk/ews`, `POST /risk/ews/:id/acknowledge`, `GET /risk/aggregates`, `GET /risk/heatmap` |
| **Audit** | `bff/audit.ts` | `GET /audit-events`, `POST /audit-events` (emit) |
| **API Keys** | `bff/apiKeys.ts` | `GET /api-keys`, `POST /api-keys`, `DELETE /api-keys/:id`, `GET /api-keys/:id/usage` |

### Customer Adapter (`src/adapters/customerAdapter.ts`)

Transforms BFF `SmbEntity` responses into UI `CustomerEntity` objects:

| BFF Field | UI Field | Transformation |

## 15. Dark Mode Implementation

### How It Works

1. **ThemeContext** stores user preference (`light`/`dark`/`system`) in `localStorage`
2. On change, adds/removes `.dark` class on `<html>` element
3. Tailwind's `darkMode: ["class"]` config activates all `dark:` variants
4. All colors use CSS custom properties — the `.dark` block in `index.css` provides dark values
5. No component-level `dark:` overrides needed because all colors flow through tokens

### Toggle Location
`DashboardHeader.tsx` contains a dropdown with three options:
- Sun icon → Light mode
- Moon icon → Dark mode
- Monitor icon → System (follows OS preference)

### Dark Token Values
The `.dark` block in `src/index.css` provides darker variants of all tokens:
- Backgrounds flip from whites to near-blacks
- Text flips from darks to lights
- Status colors get slightly brighter for contrast
- Shadows increase opacity for visibility on dark surfaces

## 17. Replacing Demo Data with Live Data

### Current State
The dashboard renders **static demo data** from `src/data/demoData.ts`. The BFF service layer and Supabase integration are fully built but inactive because `DEV_BYPASS_AUTH = true`.

### Step-by-Step Migration

#### Step 1: Deploy Supabase Edge Functions
Each BFF service endpoint (`/customers`, `/scores`, `/risk/summary`, etc.) needs a corresponding Supabase Edge Function. The function signatures match the BFF client exactly.

Example edge function structure:
```
supabase/functions/
├── customers/index.ts        # Handles GET/POST /customers
├── scores/index.ts           # Handles GET/POST /scores
├── applications/index.ts     # Handles GET/POST/PATCH /applications
├── risk/index.ts             # Handles GET /risk/*
├── reports/index.ts          # Handles GET/POST /reports
├── audit-events/index.ts     # Handles GET/POST /audit-events
├── api-keys/index.ts         # Handles GET/POST/DELETE /api-keys
└── offers/index.ts           # Handles GET/POST /offers
```

#### Step 2: Enable Authentication
In `src/App.tsx`, set:
```typescript
const DEV_BYPASS_AUTH = false;
```

This activates `ProtectedRoute`, which checks `supabase.auth.getSession()`. Users will be redirected to `/login` if not authenticated.

#### Step 3: Replace Demo Data Imports with BFF Calls

**Before (demo data):**
```typescript
import { PILOT_METRICS, DEMO_BUSINESSES } from '@/data/demoData';

function OverviewPage() {
  return <MetricCard value={PILOT_METRICS.totalBusinesses} />;
}
```

**After (live data):**
```typescript
import { customersService } from '@/services/bff';
import { useBffQuery } from '@/hooks/useBffQuery';
import { useRequiredPortfolio } from '@/contexts/PortfolioContext';

function OverviewPage() {
  const portfolioId = useRequiredPortfolio();
  const { data, isLoading } = useBffQuery(
    () => customersService.getHealthMetrics(portfolioId),
    [portfolioId]
  );

  if (isLoading) return <MetricSkeleton />;
  return <MetricCard value={data.totalBusinesses} />;
}
```

#### Step 4: Wire Up Real-Time Events
Replace `LiveActivityTicker` (simulated) with WebSocket or Server-Sent Events from Supabase Realtime:

```typescript
// Subscribe to real-time events
supabase
  .channel('audit_events')
  .on('postgres_changes', { event: 'INSERT', schema: 'public', table: 'audit_events' }, (payload) => {
    addTickerEvent(payload.new);
  })
  .subscribe();
```

#### Step 5: Connect Report Generation
The `useReportPolling` hook is already built for async report jobs:

```typescript
const { startPolling, progress, status } = useReportPolling();

async function generateReport(template: string) {
  const job = await reportsService.create(portfolioId, { template, filters });
  startPolling(job.id);  // Polls GET /reports/:id every 3s
}
```

|---|---|---|---|
| 1 | Customer list | `DEMO_BUSINESSES` | `customersService.list()` |
| 2 | Score displays | Inline mock | `scoresService.getDistribution()` |
| 3 | Underwriting pipeline | Inline mock | `applicationsService.getPipelineStats()` |
